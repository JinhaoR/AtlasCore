# First Firefox adapter (D15)

Architecture recorded before implementation on 2026-09-30. This is a development WebExtension for ordinary top-level HTTP(S) navigation. AtlasCore remains the decision engine. Electron, Context Whitelist, provider databases, authentication handling, and resource filtering remain excluded.

## Architecture and API choices

Use Manifest V2 with a persistent background page for this Firefox-only slice. Firefox continues supporting V2. Persistence avoids event-page suspension losing live tab/Journey bindings during an attempt. A later V3 port must explicitly handle that lifecycle; Firefox V3 uses event pages, not Chrome service workers. [Mozilla support statement](https://blog.mozilla.org/en/firefox/firefox-manifest-v3-adblockers/), [background manifest](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background).

`extension/` is a separate private TypeScript package with a local `@atlas/core` dependency. Build Core, then bundle its public exports and extension entry points with esbuild. No browser imports or new runtime dependencies enter Core. Type declarations and test-only IndexedDB emulation are development dependencies.

| Layer | Responsibility |
| --- | --- |
| Background | Construct one controller, injected clock, repository, and adapter; register listeners before asynchronous initialization. |
| Adapter | Hold top-level requests, bind fresh opaque contexts to native tabs, correlate redirects/arrival/failure, translate explicit UI commands, execute Core results, and remove denied retained content. |
| Core | Validate aggregate state; decide policy, waits, grants, Journey limits, and protected policy transitions; serialize and verify commits. |
| Repository | Extension-origin IndexedDB transactions implementing `AtlasRepository`; atomic initialization, compare-and-swap, complete snapshots, and commit receipts. |
| UI | Initial setup, destination launchers, selected-tab access controls, deadlines, Journey status, and diagnostics. No authorization rules or direct storage writes. |

Use asynchronous blocking `webRequest.onBeforeRequest`, filtered to `main_frame` and HTTP(S), with a frame-zero check. Each redirect target goes through the same gate. No request bodies, cookies, headers, iframe requests, images, scripts, or analytics are inspected. Use `webNavigation.onCommitted` for actual document arrival, error events for failed execution, and tab removal for binding loss. `tabs` provides native handles and replacement of denied content. [Blocking API](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/webRequest/onBeforeRequest), [arrival event](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/webNavigation/onCommitted).

The UI uses `runtime.sendMessage`. Only the extension's own UI URL and extension ID may call the bridge. Messages have closed shapes; no content scripts, external-message listener, or web-accessible UI is provided. Browser events never become policy commands. [Message sender](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/MessageSender).

## Necessary refinements to earlier assumptions

1. **Explicit Journey start.** Firefox's useful transition/intent metadata arrives after the blocking decision. A redirect to a Whitelist root is not proof of a deliberate new attempt. The control page therefore offers destination Open buttons and Start Journey in a selected tab. Ordinary Whitelist navigation still works. Clicks, redirects, reloads, popups, and time passing never start or renew an attempt automatically.
2. **Narrow execution protocol.** D12's generic runtime ledger and DECISION/ADOPT API remain proposals. D15 adopts a smaller browser-specific protocol over the implemented D14 controller. Pure plans and cached assessments remain non-executable. The adapter may release exactly the currently held request after a fresh saved controller ALLOW, required intermediate recording, and a final correlation check. This changes the earlier blanket statement that every controller assessment needs an unimplemented ADOPT API; it does not change Core's decisions or duplicate its precedence rules.
3. **Transactional storage.** `storage.local` has no transaction/CAS API. Use Firefox's extension-origin IndexedDB instead of pretending get/set meets `AtlasRepository`. Writes use strict-durability read/write transactions and publish only on transaction completion. A receipt and the complete envelope share one transaction. Reads overlap the same stores and fence prior transactions. An absent receipt proves non-commit only after that transaction barrier, never from an absent latest marker. [Transactions](https://developer.mozilla.org/en-US/docs/Web/API/IDBDatabase/transaction), [durability](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/durability).
4. **Explicit setup.** First-run UI submits a complete initial Whitelist/Blacklist to Core validation. Initialization works once in an empty repository. Missing/corrupt records in an initialized database fail closed. Setup cannot edit active policy. Vault UI is deferred; later policy editing must use Vault. Whole-profile deletion, deliberate extension removal, and device-clock tampering remain outside this prototype's protection.
5. **Development configuration.** Use a 10-second Access wait, 60-second confirmation window, 60-second grant; a 30-second Vault wait and 60-second confirmation window; a five-minute Journey and 12 hops. These are visible development settings, not adopted production product durations. Existing terms remain frozen by Core.

## Request and context protocol

- Register listeners synchronously. Until controller startup/reconciliation succeeds, requests are held or cancelled, never allowed through an initialization fallback.
- Every tab lifetime gets a fresh opaque context. Popups and duplicated tabs get separate identities; no Journey inheritance. Core's existing hostname grants remain shared across contexts.
- Serialize adapter commands and request adoption around the shared controller. Capture the current request identity, exact transient URL, context generation, and Journey identity. A newer request or closed tab invalidates an earlier result even while persistence is pending.
- Normalize the actual request with Core. Call CHECK_NAVIGATION. On ALLOW, record any intermediate Journey step through RECORD_JOURNEY_NAVIGATION and await its verified save before releasing the request. Same-host repetition does not renew a deadline or add a hop; Core decides that behavior.
- Root requests do not complete a Journey. Only a matching committed arrival can record the root return. Redirecting through the root without a document arrival keeps the attempt active. Failed execution does not refund hops or restart clocks. Unmatched arrival or lost correlation ends the binding before ordinary reevaluation.
- Non-ALLOW results cancel the request and open the private extension page using `tabs.update`, rather than exposing a privileged page as a web-accessible redirect. UI replacement/closure must be observed before reporting removal. Failed replacement falls back to closing the affected tab; failures remain visible.
- Greylist Start and Confirm are separate user actions. The `CONFIRM_ACCESS` bridge command changes state only. D16 adds an explicit `CONFIRM_ACCESS_AND_OPEN` UI command: after a saved confirmation, it issues a fresh homepage GET only if the same context, generation, and destination remain. Open site home also issues a new GET. Every request receives a new Core assessment. Blocked POSTs and credential-bearing URLs are never replayed. Only sanitized origins are retained for those commands. Browser-observed full URLs remain in transient request correlation; Core snapshots and UI views expose hostname-only decisions. The explicit Open Journey command can carry the URL typed by the user to the adapter.
- Recheck displayed documents periodically and after relevant lifecycle changes. Rechecks cannot invent Journey hops. If adoption has moved the Journey but arrival is still pending, retain the original decision's deadline as a conservative execution guard and reconcile before a new content assessment. Unexplained target changes lose Journey binding. Core continues making every subsequent permission decision.
- Owner restart creates new context identities. Existing controller recovery ends old Journeys before readiness, while original Access/Vault timestamps remain intact. Unknown storage outcomes stop navigation and await explicit recovery; no confirmation replay.

## Coverage and limits

HTTP(S) top-level requests exposed to `webRequest` are the pre-request enforcement boundary. `webNavigation` and periodic tab checks also reconcile visible history/cache restoration and already-open tabs, but those observations occur after display. Internal Firefox pages, protected Mozilla origins, other extensions, private browsing, downloads, non-HTTP schemes, and iframe content are not claimed as governed entry points. This is not universal navigation lockdown or zero network egress. Background failure/removal is a browser lifecycle limit, not a permissive Core decision.

Firefox does not provide a common request ID in `webRequest` and `webNavigation`; the initial mapping uses the latest held URL, event ordering, and live context/Journey identity. Ambiguity fails conservatively. Native tests must exercise redirects and late/failed callbacks. Other extensions may interfere with requests. Browser scheduling can delay content removal; the UI must not claim success before arrival/closure is observed.

An address entered manually in an active Journey tab can also fit inside the bounded exception: the pre-request API cannot reliably distinguish that action from continuation. The Cancel Journey control explicitly ends the attempt. No authentication-only or necessity guarantee is claimed. Native evidence and the late initial blank-page regression are recorded in the [acceptance evidence](acceptance-tests.md#firefox-adapter-evidence-d15).

Repository unit tests use IndexedDB emulation; native Firefox tests exercise the real backend and extension. Neither establishes physical power-loss durability, authentication-provider compatibility, or exhaustive browser event coverage. Receipt records are retained for reconciliation; compaction is deferred and their growth is a development limitation.

## Validation plan

Use the real Core and fake time with mocked Firefox events for allowed and denied navigation, explicit Greylist confirmation, fixed Journey paths, redirects, context isolation, superseded requests, failed saves, untrusted messages, cancellation, and visible-content expiry. Separately test repository CAS, atomic replacement, initialization, corruption, receipts, and restart loading.

Use an isolated native Firefox profile and synthetic local hostnames for root → provider → identity → root. Check actual page arrivals, exact fixed deadline, ended Journey, unchanged policy, no grants, and a denied later visit to an intermediate. Include independent server evidence where claiming a request was withheld. Never use real accounts, authentication tokens, or Ladok credentials in the test.

## Prototype interface and diagnostics (D16)

Authorized on 2026-09-30: improve the Firefox interface, browsing flow, diagnostics, and real-site investigation. Core's source, rules, configuration semantics, and public API stay unchanged. Existing short timing values remain clearly labelled prototype settings; this task does not select production durations.

- The control page presents Whitelist destination launchers, one selected tab's access state, a Journey summary, and secondary diagnostics/recovery panels. Blocked navigation opens the same private page focused on that tab. Context selection never silently switches to another tab after closure.
- Opening a Whitelist destination is an explicit Journey command. Ordinary Whitelist browsing still uses Core's gate. A rejected start closes the temporary blank tab. The toolbar reuses a control page instead of accumulating duplicate control tabs.
- Countdown text is presentation only. Confirm is shown only for Core's REQUIRE_CONFIRMATION result. An explicitly labelled **Confirm and open** command may combine a saved Core confirmation with a fresh homepage navigation in the same still-bound tab. Failed saves, stale request/tab correlation, and changed destinations never navigate. This is an explicit user action, not automatic permission at readiness. No blocked POST or provider URL is replayed.
- Read-only views and diagnostics can be inspected while a commit is pending. They expose only the controller's last verified snapshot and current owner status. Mutating commands remain serialized. Toolbar indicators show the current Core result and bound Journey without deriving new access rules.
- Diagnostics retain at most 200 entries in background memory. Entries contain local sequence/navigation IDs, time, opaque context/tab identity, normalized hostnames, event type, Core outcome/reason, and a compact Journey summary. Never include paths, queries, fragments, request bodies, headers, cookies, page text, browser error messages, or credentials. Clear/export are explicit UI actions; restart clears the buffer. Diagnostics are observations, never a trust graph, provider registry, or authorization input.
- Real-site checks use fresh isolated profiles and public sign-in entry points. Stop before submitting account identifiers, credentials, consent grants, or account-changing actions. Report public-page/redirect evidence separately from authenticated success. Live checks retain only sanitized diagnostic summaries; discard their browser profiles and suppress raw browser logs. Provider-specific selectors belong only in optional investigation scripts, never in the adapter.

New evidence and any concrete event-handling fixes are recorded with the prototype tests and the real-site report. No account compatibility claim follows from a sign-in form merely appearing.

`GET_VIEW` and `GET_DIAGNOSTICS` are read-only private-UI messages and do not join the mutating queue. The former exposes the last verified snapshot, including a COMMITTING or RECONCILING status when applicable. UI actions stay disabled until READY. `CLEAR_DIAGNOSTICS` clears only memory. Redirect diagnostics use informational `onBeforeRedirect`; the following target still needs its own blocking Core check. [Firefox redirect event](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/webRequest/onBeforeRedirect).

The toolbar reuses a control tab while preserving blocked-site tabs. Its per-tab badge shows `J` for a currently allowed Journey, `WAIT`, `GO` for a Core confirmation result, or `!` for other blocked/unavailable states. These are observations of Core responses. [Firefox badges](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/browserAction/setBadgeText).
